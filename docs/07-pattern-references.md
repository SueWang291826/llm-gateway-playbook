# 07 · 模式出处对照：每个机制背后的成熟方案

> 方法论立场：**成熟模式负责「方向正确」，本地化适配负责「真正有效」**。这张表记录每个机制"抄"的是谁、以及我们改了什么——后者才是工程价值所在。

## 总表

| 机制 | 出处 | 本项目的适配差异 |
|---|---|---|
| 熔断器状态机 | Netflix **Hystrix** / Resilience4j | 状态放 SQLite 跨 8 worker 共享（教科书是单进程内存）；「超时不算失败」防误熔断；half-open 试探原子授予 |
| Map-Reduce | Google MapReduce；LangChain `map_reduce` 摘要链 | 加了 LangChain 没有的：白名单筛选、全局切片预算、目录轮转公平分配、跨轮缓存、对冲汇总 |
| 对冲请求 Hedged Requests | Google **《The Tail at Scale》**（Dean & Barroso, CACM 2013）；gRPC hedging | 原文治尾延迟（取先到）；我们叠了「预算内主模型优先」的质量偏好——快之上要有好 |
| 滑动窗口 + 渐进摘要 | LangChain `ConversationSummaryBufferMemory`；memGPT 记忆分层 | 摘要只追加不重写（前缀稳定性硬约束）；增量后台合并不阻塞当轮；覆盖指纹防误命中 |
| 前缀缓存适配 | vLLM automatic prefix caching | 我们是纯代理无权重，无法开缓存本身——能做的是把 prompt 前缀做成严格稳定，让上游缓存替我们省算力 |
| Stale-While-Revalidate | **RFC 5861**（HTTP 缓存扩展） | 用在工单列表：慢源（97~270s 大窗查询）过期也秒回旧值，后台刷新 |
| 头尾采样 | 日志诊断惯例（错误集中在文件首尾） | 单文件超 6 片取头尾各半 + 「中段已省略」标注；120MB 心跳日志 480 片→6 片 |
| 轮转调度 Round-Robin | 经典公平调度 | 全局 24 片预算按父目录轮转分配——防单一大目录垄断、保模块覆盖公平 |
| 分级截止期 | 分布式系统 deadline propagation | prep/切片/map/reduce 四级独立死线 + 波次公式 `max(下限, ⌈n/并发⌉×单片超时+30)` |
| SSE 心跳保活 | SSE 反向推流惯例 | 每 5s `: keepalive` 注释行 + 「先开流再执行」+ 失败走 200 结构化文案 |
| 分布式追踪 | OpenTelemetry 语义约定；Langfuse | 直调绕过执行器时本地补挂 tracer（超时/取消也留痕）；perf 分阶段耗时透传前端 |
| 启动探针 + 熔断预置 | 微服务健康检查惯例 | 启动 ping 失败的档位开机即预置熔断 open——「服务一起来就知道」，不是「用户先踩雷」 |

## 三条最值得展开的

### 1. 熔断器：教科书模式的多进程改造

单进程熔断器到处都有现成实现，直接用会踩的坑：**8 个 worker 各自计数，阈值失真**（实际连续失败 3 次，最坏要 24 次才全网拦截）。改造点：

- 状态进 SQLite（WAL + busy_timeout），每个操作开短连接——多进程安全且无部署依赖；
- `open → half_open` 的试探授予用**条件 UPDATE 原子完成**（`WHERE state='OPEN' AND opened_at <= now-cooldown`），多进程同时冷却到期也只有一个人能拿到试探资格；
- `record_failure` 在 half_open 状态下直接回 open（试探失败立刻重新熔断）。

还有一条容易忽略的规则：**超时不计入失败**。「慢」不是「挂」，把重负载下的正常慢速计入熔断，会把最忙的模型封掉——熔断器本意是保护系统，结果先杀了好人。

### 2. 对冲请求：论文场景 vs 我们场景

《The Tail at Scale》的场景：RPC 尾延迟伤害整体可用性，**同时发两份、取先到**，成本略增换 P99 大降。gRPC hedging 同思路。

我们的场景多一个维度：**汇总质量直接决定产品价值**。纯取先到会让 flash 保底（质量低）总是赢——它不排队、总是先完成。所以语义改成：**预算内主模型优先（质量），预算外才用先到的保底（稳定）**。同一个骨架，不同的取舍——这就是"适配"的含义。

### 3. 前缀缓存：无权重方的配合姿态

vLLM 的 prefix caching 在推理服务端自动工作，前提是**请求的前缀真的相同**。多轮对话代理天然破坏这个前提（每轮 prompt 都变）。代理层能做的全部：

1. 结构固定（system → 摘要 → 近期原文，顺序永不变）；
2. 摘要段只追加（旧内容恒为新内容前缀）；
3. 摘要 prompt 要求"复述并续写"而非"重新总结"。

这不能让缓存命中率变 100%，但把"每轮全 miss"变成"增量部分 miss"——**在别人的系统边上工作，先弄清自己的行为怎么影响它**。

## 一句话

不要重新发明模式，也不要原样照抄模式。**先知道它解决什么问题，再问自己的场景差在哪，差异处就是你的设计工作所在。**
