# 04 · 日志分析 Map-Reduce 管线：三次演进与预算设计

> 场景：一个运维工单带几百个附件文件（日志、配置、压缩包，单个文件可达 120MB），要 LLM 交叉比对给出「问题模块 / 根因 / 修复建议」。单 agent 串行读文件不可行（慢、上下文互相挤占、一步卡全盘超时）。解法是经典 Map-Reduce：**切片 → 并发小结 → 汇总**。这篇记录管线怎么被真实规模逼着进化了三版。

## 管线全貌（最终形态）

```
prep（预算 120s）
  ├─ 并行下载附件（Semaphore 4，按 URL hash 去重）
  ├─ 递归解压，chunked 流式计数（超限截断不爆内存）
  └─ 产出文件清单：path / size / 扩展名
        │
plan_slices（预算 60s）
  ├─ 扩展名白名单过滤 → 白名单外文本 / 二进制 → 本地标注（0 次调用）
  ├─ 白名单文件 → 400 行 / 64KB 切片；单文件 ≤6 片，头尾采样
  └─ 全局预算 24 片，按父目录轮转分配；预算外 → overflow 本地标注（0 次调用）
        │
map（Semaphore 8 并发；预算 = max(300s, ⌈片数/8⌉×90s+30s)）
  ├─ 工单描述 → 1 片（每轮重新小结，不缓存）
  ├─ 每个文件切片 → flash 档小结（结构化：根因线索/关键日志行/可疑点）
  ├─ 文件切片小结按 内容+标签+模型 哈希 → 跨轮缓存（追问轮命中 0 调用）
  └─ 单切片失败/超时 → 标注跳过，不阻塞整体
        │
digest 预算（总量 50k 字符）
  └─ 单份小结上限 = max(1500, min(4000, 50000 // 小结数))——片多自动收紧
        │
reduce（预算 150s，对冲并行：主模型 + flash 保底）
  ├─ 首步判定问题模块；非目标域工单直接给简短结论不深挖
  ├─ 全部证据内嵌 + 首行禁核验指令 + CLI 级禁工具
  └─ 预算内主模型完成用主模型（质量优先）；否则用先完成的保底（稳定必达）
```

## 三版演进：同一个问题的三层答案

| | v1 | v2 | v3（现行） |
|---|---|---|---|
| **筛选** | "疑似文本"启发式，无差别切片 | 25 扩展名白名单，名单外本地标注（0 调用） | 同 v2 |
| **切片大小** | 1500 行 / 256KB | **400 行 / 64KB**，单文件 ≤6 片头尾采样 | 同 v2 |
| **数量控制** | 50 片保护上限（超了就合并成 batch） | 同 v1 | **全局预算 24 片 + 目录轮转**，预算外 overflow 本地标注 |
| **暴露的问题** | 436 文件 → 70+ 无价值切片，60s 整齐全灭（事故④） | 469 个**合法** .log → ~440 片合并成巨型 batch，再全灭（事故⑤） | — |

演进逻辑：**v1 回答"怎么切"，v2 回答"什么值得切"，v3 回答"切得起多少"**。每一版都是下一版的事故逼出来的——这不是设计失败，这是真实规模的学费。

## 关键设计逐个说

### 1. 白名单：筛选发生在调模型之前

不是所有文件都值得一次模型调用。二维码图片、无扩展名产物、无关文本——白名单外一律本地标注「非分析类文本，共 N 个」并进入 reduce 上下文（让汇总模型知道**有这些东西存在**，只是没逐个分析）。**筛选发生在调用之前，节省的才是 100% 成本。**

### 2. 头尾采样：错误集中在边界

日志的错误信息几乎总在文件头（启动崩溃）或尾（结束前异常），中间大段正常输出。单文件超 6 片时取头尾各半，切片内注明「中段已省略」。实测一个 120MB 心跳日志：480 片 → 6 片，信息损失对排障几乎为零。

### 3. 目录轮转：预算的公平分配

全局 24 片怎么分？按文件大小贪心的话，一个巨大的心跳日志目录会吃光预算，其他模块目录一片拿不到——分析就瞎了一只眼。轮转分配：文件按父目录分组、目录按数据量降序，**像发牌一样每目录轮流各拿一片**，直到预算发完。

```
目录A(心跳日志, 200MB):  a1 → a2 → a3 → ...
目录B(导航模块, 5MB):    b1 → b2
目录C(调度模块, 3MB):    c1 → c2
预算 6 片 → A:{a1,a2,a3} B:{b1} C:{c1}   # 每个模块都有代表
贪心 6 片 → A:{a1..a6} B:{} C:{}          # B、C 完全失明
```

**宁可浅尝遍地，不可垄断一处。**

### 4. Overflow 标注：诚实优于假装

预算外的文件本地列出路径「超出预算未分析，共 N 个」，并提示「需深挖某个文件请点名追问或切深度模式」。宁可明说没看，不要假装看过——**汇总模型不知道的边界，必须显式告诉它**。

### 5. 跨轮缓存：追问轮 0 调用

文件切片的小结按「内容哈希 + 标签 + 模型」缓存。用户第二轮追问时，同样的文件零次模型调用直接吃缓存。刻意**不缓存**的：工单描述切片（每轮用户焦点不同，重新小结）和含轮次相关标签的切片（description 类标签每轮变化，天然不命中）。

### 6. Reduce-only：追问轮不退化

无新附件的追问轮不再退回单 agent 重跑（旧实现的行为），而是把已有全部小结 + 对话上下文头尾截取 8000 字，单次直答。**管线没有 map 活儿时也保持管线形态**——路径统一，行为可预测。

### 7. 分级预算：挂住的只烧自己那份

prep / 单切片 / map 总预算 / reduce 四级独立死线；map 总预算随片数自适应放大（波次公式），但单切片挂死最多赔自己一格。见 [02-postmortems.md](02-postmortems.md) 事故③、参考实现 [`patterns/staged_budget.py`](../patterns/staged_budget.py)。

### 8. 实时进度流（仪器 + 体验一体）

`stream=true` 时先开流再执行：首 chunk 立即下发 → 5s `: keepalive` 心跳 → 阶段事件走 `delta.reasoning_content`（思考流，业界惯例字段）+ 结构化 `mr` 字段 → 失败以 200 + 结构化文案收尾 → 断连取消分析释放锁。前端实时渲染，完成后折叠保留。

perf 透传字段（分析完在响应 meta 里可查）：`prep_ms / map_total_ms / map_ok / map_failed / map_cached / map_slices / reduce_ms / reduce_model / fallback_used`——**每个阶段的耗时和结果可归因**，是下一次调优的输入。

### 9. 全失败护栏

map 全部失败才算整体失败；只要有本地标注/缓存小结存在，reduce 仍给出结论。纯二进制工单（零次模型调用）也能出「这些附件需要人工查看」的诚实报告。

## 效果数据

| 指标 | v1 | v3 |
|---|---|---|
| 436~469 文件工单的切片数 | ~440 片（无界） | ≤24 片 + 1 描述片（有界） |
| 首轮分析结果 | 60s 整齐全灭 / batch 90s+ 全灭 | 约 1 分钟出结论 |
| 追问轮模型调用 | 重跑文件分析 | 文件切片 0 调用 + reduce-only 直答 |
| 耗时可预测性 | 取决于文件数（无界） | 四级预算内有界 |

## 出处

Map-Reduce 范式（Google）+ LangChain `map_reduce` 摘要链是骨架；白名单/头尾采样/轮转预算/跨轮缓存是对冲本地规模问题的加装。详见 [07-pattern-references.md](07-pattern-references.md)。
