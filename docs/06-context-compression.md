# 06 · 上下文压缩：滑动窗口 + 渐进摘要 + 前缀缓存适配

> 问题：多轮对话把**完整历史线性拼进 prompt**，无截断无摘要。实测几轮追问后单轮 prompt 达 **35k~66k 字符**——这是"多轮分析 28~43 轮里 62.5% 撞 600s 超时"的第一主因。

## 设计：近的留原文，远的存摘要

```
prompt 结构（固定三段，顺序永不变）
┌────────────────────────────────┐
│ [系统提示]                      │ ← 固定
├────────────────────────────────┤
│ [Earlier conversation summary] │ ← 更早的历史压缩成的摘要，只追加不重写
│  ...                           │
├────────────────────────────────┤
│ [最近 K 条原文]（默认 6 条）     │ ← 滚动窗口
└────────────────────────────────┘
```

触发条件：消息数 > K 且总字符 > 阈值（默认 20k）。不满足则走原样拼接——**小请求不付压缩的税**。

## 三个关键机制

### 1. 增量合并：压缩不阻塞当前请求

摘要按 conversation_id 文件缓存（8 worker 共享）。命中缓存后：

- **当前请求**：直接用缓存摘要 + 水位之后的增量原文，立刻返回（不等压缩）；
- **后台任务**：`asyncio.create_task` 把增量并入摘要、推进水位 → **下一次**请求生效。

即首次超窗同步压一次（flash 档，1~2s），之后每轮都是"先答后压缩"。

### 2. 前缀稳定性：喂饱上游 prefix cache（硬约束）

上游推理服务普遍有前缀缓存（vLLM 的 automatic prefix caching 等）：两次请求的 prompt 前缀相同，第二次省大量重复计算。代理层没有权重、控制不了缓存本身，能做的是**把 prompt 前缀做成严格稳定**：

- 三段结构顺序固定；
- 摘要段**只追加不重写**（旧摘要恒为新摘要的前缀）；
- 摘要生成的 prompt 里显式要求"复述并续写"而不是"重新总结"。

这是一条**硬约束**：任何压缩策略的改动，先过"前缀是否稳定"这一关。

### 3. 防误命中：指纹校验

缓存 key 用 conversation_id，但历史可能被截断/重排。命中前校验**覆盖指纹**（首条消息 + 边界消息的哈希）——指纹不匹配宁可重压，不拿错摘要。无稳定 conversation_id 的无状态请求，按**消息前缀哈希**做 key（同一 client 多次请求历史前缀一致，命中率高）。

## 边界：哪些路径根本不该压缩

- **有 CLI session 的状态化请求**：走 resume 语义，只发最新一条 user 消息，历史在 CLI 侧——压缩根本不介入；
- **压缩真正作用的**：无状态大历史 + 状态化首次请求 + session 丢失重试。

验证效果时别拿错路径（拿 session resume 的请求去看压缩生效，永远看不到）。

## 兜底与护栏

- `PROMPT_HARD_CAP_CHARS`（默认 400k）：不管压缩与否，prompt 硬上限截断——防异常/恶意请求打爆后端；
- 摘要生成用最便宜的 flash 档，失败不阻塞（退回原文拼接）；
- 观测：响应 meta 带 `summary_compressed` 标记。

## 效果

- 多轮追问的 prompt 尺寸从滚雪球（35k~66k 且单调增长）变为**有界**（摘要 + 最近 6 条）；
- 配合前缀稳定，多轮请求对上游 prefix cache 的命中率显著提升（代理层能做的全部）；
- 62.5% 的 600s 超时率降为分钟级稳定（与 Map-Reduce 管线叠加效果）。

## 出处

滑动窗口 + 渐进摘要 = LangChain `ConversationSummaryBufferMemory` / memGPT 记忆分层的思路；前缀稳定性 = 推理服务 prefix caching 的代理层适配。详见 [07-pattern-references.md](07-pattern-references.md)。
