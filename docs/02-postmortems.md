# 02 · 六次线上事故复盘

> 这篇是整个仓库的核心。六次事故，每一次都走同一条路径：**现象 → 取证 → 根因 → 修复 → 防复发**。
> 所有耗时数据为真实测量值；内部标识已匿名化（"旗舰模型"= 最强档位，"flash 档"= 最快最便宜的档位）。

## 复盘的固定格式

每个事故按四段讲，每段一句话能收口：

1. **现象**：用户看到了什么（精确到报错码和频率）；
2. **取证**：拿到什么证据、证据是怎么来的（没有服务器权限，全靠 [03-blackbox-debugging.md](03-blackbox-debugging.md) 的三件仪器）；
3. **根因**：能解释全部现象、且修复后现象消失的那个解释；
4. **修复与防复发**：代码怎么改 + 什么测试/机制保证不再犯。

## 事故 ①：上线即全量 500

**现象**：新版本一上线，所有请求 100% 返回 500。不是概率性，是全量。

**取证**：全量挂反而好查——必然是新代码的公共路径问题。本地构造请求复现，堆栈直指一个 `UnboundLocalError`。

**根因**：前一轮重构把执行逻辑提取成闭包函数，在「会话丢失重试」分支里给某个变量**重新赋值**。Python 的规则：函数体内任何位置出现赋值，该变量即被判定为局部变量——于是第一处读取直接抛 `UnboundLocalError`，异常被兜底捕获后转成裸 500。

**修复与防复发**：闭包顶部建立本地别名，重试只重绑别名。更重要的是补了**端点级测试**（TestClient 从 HTTP 入口打进来，stub 掉模型层）——此前只有单元测试，这条路径没有任何测试覆盖，所以重构引入的崩溃测试拦不住。

**教训**：*重构闭包/嵌套函数时，一个变量赋值位置的变化就能瘫痪全服务。没有端点级测试的重构是裸奔。*

## 事故 ②：SSE 零字节，被网关掐死

**现象**：Map-Reduce 分析跑 1~2 分钟，客户端连接经常在出结果前被掐断——**HTTP 200 但 0 字节内容**。另一种形态：分析失败时裸 500。

**取证**：服务日志显示分析正常进行中，连接却被对端关闭。时间轴对齐后发现：连接建立到被掐的间隔 ≈ 中间网关的空闲超时阈值，而这段"空闲"里服务端确实一个字节都没发。

**根因**：实现是「**先算完、再开流**」。SSE 连接建立后长时间无字节，中间网关判定空闲直接掐线。分析恰恰需要安静跑一两分钟——必踩。

**修复与防复发**（四件套，成为所有流式接口的标配）：

1. **先开流再执行**：连接建立后第一个 chunk 立即下发；
2. **每 5s 一条 `: keepalive` 心跳**（SSE 注释行，客户端无感，网关看到字节流过就不掐）；
3. **失败也走 200**：以 200 + 结构化中文文案收尾，前端能显示"分析未完在：原因"，不再白屏报错；
4. **断连止损**：用户点停止/关页面 → 服务端立刻取消分析、释放会话锁，不烧无谓的算力。

**教训**：*流式接口的三条铁律——先开流、有心跳、失败也走 200。附带收获：这次为排查加的实时思考流（每个阶段/切片的进度事件）后来成为事故 ④⑤⑥ 最重要的取证仪器。*

## 事故 ③：连续分析 409 锁超时

**现象**：同一工单连续点两次分析、或某次分析中一个切片卡死，后续请求全部 409（会话锁等待超时）。

**取证**：日志显示一个切片占着会话锁 600 秒不放（复用了全局执行超时），而锁等待上限只有 10 秒——必然 409。

**根因**：**没有分级预算**。Map-Reduce 复用了单次执行的 600s 超时，一个挂住的切片有能力烧光全局时间并锁死会话。

**修复与防复发**：四级超时预算——prep / 单切片 / map 总预算 / reduce 各自独立死线：

```
map 总预算 = max(下限, ⌈切片数 / 并发数⌉ × 单切片超时 + 30s 宽裕)
```

切片越多预算自动放大（波次公式），但**任何一个切片挂死，最多赔掉它自己那一格**。参考实现见 [`patterns/staged_budget.py`](../patterns/staged_budget.py)。

**教训**：*预算要分级。挂住的东西只能烧自己的预算，不能烧全局的。*

## 事故 ④：436 个文件，切片 60 秒整齐全灭

**现象**：某工单解压出 436 个文件。思考流显示：附件准备 3.0s、工单描述切片 21.2s 成功，然后**所有文件切片整整齐齐全部在 60.0–60.1s 超时**。

**取证**：那个「整整齐齐」就是破案关键。如果是网关抖动或模型不稳定，超时点应该散乱；全部精确死在 60 秒——**正是我们自己设的切片超时值**。说明不是没人应答，是任务在 60s 内根本跑不完。对照证据：1.5KB 的描述切片 21s 就成功了。

**根因**（两个叠加）：

1. **无差别切片**：436 个文件里大量二维码图片、无扩展名产物、无关文本，被"疑似文本"启发式判为文本，占了 70+ 个切片；
2. **切片过大**：单片目标 1500 行/256KB，这种体量内联进 prompt，flash 档 60s 跑不完。

**修复与防复发**（「先筛、再缩、后兜」）：

- **先筛**：25 种扩展名白名单（.log/.txt/.json/.conf…）之外的文本 → 本地标注（"非分析类文本，共 N 个"），**零次模型调用**；二进制同样本地标注；
- **再缩**：切片目标 1500 行/256KB → **400 行/64KB**；单切片超时 60→90s（配合小切片，90s 反而宽裕）；
- **后兜**：单文件最多 6 片，取**头尾各半**采样——日志错误集中在文件头（启动崩溃）和尾（结束前异常），中间大段正常输出砍掉，切片内注明「中段已省略」。那个 120MB 的心跳日志从 480 片降到 6 片。

**教训**：*超时点整齐得像用尺子画的，凶手就是你自己的预算值。以及：不是所有文件都值得调一次模型——筛选发生在调模型之前，成本才是零。*

## 事故 ⑤：白名单生效了，巨型 batch 切片又全灭

**现象**：修复后复测另一个工单——469 个文件，**全是合法 .log**。白名单完美生效（二进制/非日志零调用），但 ~440 个切片在合并环节被归并成「某某等 10 个切片」式巨型批次，**又全部超时**：90.1s ×6 批、117.5s、163.2s、179.8s、180.0s、207.6s，全军覆没，仅一个小批次 73.2s 成功。

**取证**：失败与内容无关（合法日志、白名单内），只与「切片数量无上限」相关。469 个文件哪怕个个值得分析，物理上也跑不完。

**根因**：问题的本质从「**筛选**」升级为「**预算**」——合法内容的规模本身超过了可分析总量。

**修复与防复发**（这个分支里最值得记录的设计）：

1. **全局切片预算**：文件切片总数封顶 24 片，不管输入多少文件；
2. **目录轮转分配**（点睛之笔）：文件按父目录分组、目录按数据量降序，然后像发牌一样**轮转**——第一轮每个目录最大的文件各拿一片，第二轮再各拿一片，直到预算发完。若按大小贪心，一个巨大的心跳日志目录会吃光预算，其他模块目录一片没有，分析就瞎了一只眼。**轮转保证每个模块目录的头部切片都入选：宁可浅尝遍地，不可垄断一处**；
3. **预算外文件诚实标注**：本地列出「超出预算未分析，共 N 个，路径如下」，提示用户点名追问或切深度模式。**宁可明说没看，不要假装看过。**

从 ~440 片到 24 片有界——此后切片数量和总耗时第一次**可预测**。

**教训**：*当一个问题的修复引发同类的下一个问题，说明你在跟"规模"而不是跟"错误"作斗争——这时需要的不是更聪明的启发式，而是显式的预算与公平分配策略。*

## 事故 ⑥：汇总频繁降级 + 大 prompt 秒 500

**现象**：前端高频出现「旗舰模型汇总失败，降级 flash 重试」；78KB 级中文 prompt 在 0.4~2.0s 内直接 HTTP 500。

**取证**（三组对照实验，每组一条铁证，详见 [05-hedged-requests.md](05-hedged-requests.md)）：

| 实验 | 数据 | 结论 |
|---|---|---|
| 输入缩到 1/3，耗时纹丝不动 | 旗舰模型 37KB→228s、**12KB→206.5s**；代码模型 37KB→216.0s、52KB→216.8s | 不是模型慢，是**网关通道排队**（与输入无关）→「换更快的模型」无效 |
| 78KB 中文 prompt 秒 500 | 稳定复现，0.4~2.0s | prompt 作 argv 参数超 Linux `MAX_ARG_STRLEN`（单参数 128KB 上限）→ `execve` E2BIG，**进程根本没起来** |
| prompt 写明「不许读文件」，仍 256s | 37KB 带禁令依旧超时，事后发现模型逐个核验文件路径 | 对 agentic 模型，**prompt 级禁令是劝告不是约束**，要禁必须在 CLI 层禁 |

**根因**：三个独立根因——网关排队（外部）、argv 长度上限（进程创建层）、agentic 工具探索（模型行为层）。

**修复与防复发**（一次提交三管齐下）：

1. **对冲 Reduce**：汇总阶段同时发出主模型 + flash 保底两个请求。预算 150s 内主模型完成 → 用主模型（**质量优先**）；否则用先完成的保底结果（**稳定必达**）。总耗时 ≤1× 预算（对比原串行重试 ≈2×）。flash 通道不排队（37KB 仅 76.4s），所以保底基本必达；
2. **prompt 改走 stdin**：子进程 stdin=PIPE 写入，根除 argv 限制；
3. **CLI 级禁工具**：`--tools ""` 关闭工具集。两个工程细节：该参数是**可变参数，必须放在 `-p` 之前**，否则会吞掉 prompt（实际踩过）；老版本 CLI 不认识会硬报错，所以加**运行时探测**（启动时 grep `--help`，支持才用）。

**教训**：*三个根因三个层次（网关/内核/模型行为），一次"汇总慢"的表象把它们叠在一起。只有把变量一个一个隔离开，才能看见各自的手。*

## 总账

| 事故 | 类型 | 修复后同类问题复发？ |
|---|---|---|
| ① | 重构引入 | 否（端点级测试覆盖） |
| ② | 时序/协议 | 否（流式四件套成为标配） |
| ③ | 资源预算 | 否（四级预算 + 波次公式） |
| ④ | 规模-筛选 | 否（白名单+采样+小切片） |
| ⑤ | 规模-预算 | 否（全局预算+轮转） |
| ⑥ | 多层叠加 | 否（对冲+stdin+CLI禁工具） |

六次里 ①② 是早期重构引入的（当场修复 + 补端点测试），③④⑤⑥ 是**新机制在真实数据规模下的必经演进**——436/469 个文件这种规模测试环境造不出来，白名单、预算、轮转这些设计只能被真实规模逼出来。衡量标准不是「出过几次事故」，而是**每次是否闭环、同类是否再犯**。
