# 01 · 四层防御：LLM 网关稳定性架构

> 背景：一个 OpenAI 兼容 API 包装器——对外提供 `/v1/chat/completions`（含 SSE 流式），对内把请求转成 prompt 交给 CLI agent 子进程执行。**无状态**、多 worker（默认 8）部署、worker 之间没有共享内存；上游 LLM 网关是另一个团队的，不可控也不可观测其内部。

## 为什么需要"四层"而不是一个熔断器

单一熔断器只解决「模型挂了别再撞」。但实际故障形态至少有四种：

1. **客户端畸形请求**（空消息、超大 prompt）——还没到模型就该拦下；
2. **某个档位的模型挂了**，但别名解析已经把请求路由过去——需要在路由决策时就知道；
3. **模型真的挂了**——需要熔断 + fallback；
4. **服务刚启动、模型早挂了**——不该让第一个用户去踩雷。

四层防御各管一段，纵深叠加：

```
请求
 │
 ▼
┌─────────────────────────────────────────────────────────────┐
│ ① 协议层（门口保安）                                          │
│    空 messages → 语义化 422                                   │
│    prompt 超过 HARD_CAP（默认 400k 字符）→ 截断                │
├─────────────────────────────────────────────────────────────┤
│ ② 路由层（调度员）                                            │
│    档位熔断 open → 别名解析自动降级 FALLBACK + [WARN]          │
│    （只影响别名解析；直传真实模型名照常透传）                    │
├─────────────────────────────────────────────────────────────┤
│ ③ 容错层（熔断器本体）                                        │
│    连挂 N 次（默认 3）→ open，冷却 60s → half-open 单试探      │
│    状态存 SQLite → 跨 8 worker 共享                           │
│    fallback 调用本身不查熔断（最后手段，但其结果仍计数）         │
├─────────────────────────────────────────────────────────────┤
│ ④ 探针层（晨检）                                              │
│    启动时对三档模型各发一次 10-token ping                      │
│    失败档位直接预置熔断 open + [ALERT]                         │
│    execute 前熔断快查（open 则跳过调用直接 fallback）           │
└─────────────────────────────────────────────────────────────┘
```

## 设计决策与理由

每一条都是踩过坑后定的，不是教科书默认值：

### 1. 熔断状态为什么放 SQLite，不用内存

8 个 worker 是 8 个独立进程。如果熔断状态放在进程内存里，每个 worker 各自计数：实际连续失败 3 次会变成「每个 worker 各自经历 3 次失败才熔断」，最坏 24 次失败才全网拦截，且恢复时间彼此不同步。SQLite（WAL 模式 + busy_timeout）是最便宜的多进程共享存储，单文件、无部署依赖。

### 2. 超时不计入熔断

「慢」不等于「挂」。把 timeout 计入失败计数，重负载下正常的模型会被误熔断。只有**网关级错误**（连接被拒、5xx、鉴权失败）才计数；`timeout`、`session_not_found`、`circuit_open` 这类与模型健康无关的码全部排除。

### 3. half-open 试探必须原子

冷却期到了，8 个 worker 同时放行试探请求等于没熔断。试探资格的授予必须原子：用一条带条件的 UPDATE（`WHERE state='OPEN' AND opened_at <= now - cooldown`）让**只有一个**进程能完成 open→half_open 的迁移，其余进程看到 half_open 状态继续拒绝。

### 4. fallback 调用不查熔断

fallback 是最后手段。如果连 fallback 都被自己熔断了，就彻底没有退路。fallback 的调用结果同样记录成功/失败——它自己挂了会被熔断，但主模型的 fallback 请求不被 fallback 的熔断状态拦住。

### 5. 路由层降级只作用于别名解析

用户可能拿着"公告里的模型名"直连（直传真实模型名）。如果路由层无差别降级，会出现"文档说支持 X，请求却 403/换模型"的困惑。所以：**别名解析降级（内部约定层）+ 直传透传（executor 层兜底仍在）**，两层各自兜底。

### 6. 熔断器构建失败必须降级不阻断

熔断器自己初始化失败（比如 SQLite 文件写不进）时，退化为"关闭的熔断器"（全部放行），**绝不能反过来把所有请求拦死**。保护层故障不能变成主链路故障。

### 7. 透明日志是硬性格式

- 降级必打：`[WARN] Model X failed (gateway Y). Fallback to Z used.`
- 熔断翻转必打：`[ALERT] Circuit breaker OPEN for model X after N consecutive failures`

格式固定到可以写监控规则。**用户不该先于系统发现故障。**

## 可观测性

`GET /health` 返回：

```json
{
  "status": "ok",
  "model_probe": {
    "haiku":  {"model": "...", "ok": true, "latency_ms": 812},
    "sonnet": {"model": "...", "ok": true, "latency_ms": 940},
    "opus":   {"model": "...", "ok": false, "error": "connection refused"}
  },
  "circuit_breaker": {"opus-model-id": {"state": "open", "fail_count": 3}}
}
```

健康检查只反映启动探针与熔断快照，不做实时探测（避免健康检查打挂网关）。
