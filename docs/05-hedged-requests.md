# 05 · 对冲请求：用实验定罪"网关排队"，用并行买"必达"

> 这是六次事故里最漂亮的一次定位。表象是"汇总阶段经常超时降级"，真凶藏在三个不同层面。这篇记录完整的证据链和最终的修复设计。

## 起点：一个高频告警

用户端高频出现：「旗舰模型汇总失败，降级 flash 模型重试」。汇总（reduce）阶段预算 120s，旗舰模型经常跑超。另外还有一个独立怪象：78KB 级的中文 prompt 会在 0.4~2.0s 内直接 HTTP 500。

当时流行的三个假设：

1. 模型太慢——换更快的模型？
2. prompt 太大——压缩汇总输入？
3. 模型在乱用工具——prompt 里写禁令？

## 三组对照实验，三条铁证

### 实验一：输入缩到 1/3，耗时纹丝不动 → 排队

构造与真实 reduce 同形状的合成 prompt，单消息直打 API（绕过一切中间层），只变输入尺寸：

| 模型 | 输入 | 耗时 |
|---|---|---|
| 旗舰模型 | 37 KB | 228.3s / 255.9s（两次） |
| 旗舰模型 | **12 KB** | **206.5s** |
| 代码模型 | 37 KB | 216.0s |
| 代码模型 | **52 KB** | **216.8s** |
| flash 档 | 37 KB | **76.4s** |

**判读**：输入差 3 倍，耗时几乎不变（206 vs 228s）；另一个模型加 40% 输入，耗时纹丝不动（216.0 vs 216.8s）。如果是模型在计算，输入越大应越慢——**平坦的延迟曲线指向排队**。flash 通道同期 76s，排除"整个网关挂了"，锁定"非 flash 通道排队 ~200s"。

**推论**：换模型无效（换个队排）、压缩输入无效（排队与输入无关）、加大预算只是把超时挪后。120s 预算在这个通道上**结构性必超**。

### 实验二：78KB prompt 秒级 500 → argv 长度上限

秒级失败和超时失败是**两种病**（见 [03-blackbox-debugging.md](03-blackbox-debugging.md)）。78KB 中文 prompt 稳定在 0.4~2.0s 内 500，可复现。定位到 OS 层：Linux 传**单个命令行参数**有 128KB 硬上限（`MAX_ARG_STRLEN`），中文一字三字节，prompt 作为 argv 参数传给 CLI 子进程时触发 `execve` E2BIG——**进程根本没创建起来**。

**修复**：prompt 改走 stdin（子进程 `stdin=PIPE`，write + drain + close）。一次改动根除，对任意大小成立。

### 实验三：prompt 禁令挡不住 agentic 模型 → 必须在 CLI 层禁工具

37KB 的汇总 prompt 首行写明「不要尝试读取或核验任何文件」，结果**仍然 255.9s**——事后发现模型真的在工作区里逐个核验小结提到的文件路径。

**判读**：对 agentic 模型，prompt 级禁令是**劝告不是约束**。要禁必须在工具层禁：CLI 加 `--tools ""`。两个工程细节：

1. `--tools` 是**可变参数**（variadic），必须放在 `-p` **之前**——放在后面会把 prompt 当成 `--tools` 的参数吞掉（实际踩过：CLI 报 "Input must be provided either through stdin or as a prompt argument"）；
2. 老版本 CLI 不认识该参数会**硬报错**，所以加运行时探测：启动时 grep 一次 `--help` 结果并缓存（类属性），支持才加。

## 修复设计：对冲 Reduce（Hedged Requests）

### 为什么不是重试

串行 fallback 的时序：主模型烧满 120s 预算 → 超时 → 再跑一遍 flash（~76s）→ 总耗时 ≈ 2× 预算，196s。且主模型那次纯属浪费。

### 设计

汇总阶段**同时**发出两个请求：

```
t=0     ├─ 主模型请求 ─────────────┤
        └─ flash 保底请求 ────┤
t=76s                        ↑ 保底完成，先收着
t=150s                              ↑ 预算到点 / 主模型完成
```

- **预算内主模型完成 → 用主模型**（质量优先：主模型汇总质量更高，flash 只保底）；
- **主模型未在预算内完成 → 用先完成的保底结果**（稳定必达：flash 通道不排队，76s 级，基本必达）；
- **总耗时 ≤ 1× 预算**。两份请求共享同一个截止线，先到的结果让另一份尽快取消。

降级语义从「失败后重试」变成「**并行保底**」：前端文案从"汇总失败，降级重试"改为"未在预算内完成，采用并行保底结果"——用户看到的是确定性，不是故障。

### 成本账

只有 reduce 这一次调用双发；map 阶段几十次调用照旧单发。**总调用量增加 <5%，买汇总必达。** 且预算约束下，先到的结果会尽快取消另一份——排队场景里主模型那份常被取消，实际增量更小。

### 择优语义（重要）

注意这不是"谁快用谁"（pure tail-latency hedging），而是**"预算内质量优先，预算外速度兜底"**：

| 时刻 | 主模型 | 保底 | 选择 |
|---|---|---|---|
| t=100s | 完成（ok） | 已完成 | **主模型**（预算内，质量优先） |
| t=150s（预算到点） | 未完成 | 已完成 | **保底**（必达） |
| t=50s | 报错 | 已完成 | 保底 |
| t=150s | 未完成 | 也未完成 | 整体失败（结构化文案，200） |

这个语义与 Google《The Tail at Scale》的原始对冲（纯粹治尾延迟、取先到）不同——我们在"快"之上叠了"预算内要好"的偏好，因为汇总质量直接影响产品价值。**成熟模式负责方向正确，本地化取舍负责真正有效。**

## 一页总结

| 现象 | 真凶 | 层次 | 修复 |
|---|---|---|---|
| 汇总 120s 预算必超 | 非 flash 通道排队 ~200s（与输入无关） | 基础设施 | 对冲并行：预算内主优先 + flash 保底必达，≤1× 预算 |
| 78KB prompt 秒 500 | argv 单参数 128KB 上限 → E2BIG | 内核 | prompt 走 stdin |
| 带禁令仍 256s | agentic 模型 prompt 禁令无效，实际在核验文件 | 模型行为 | CLI 级 `--tools ""`（运行时探测支持） |

**方法论要点：三个真凶分别在基础设施/内核/模型行为三个层面，"汇总慢"的表象把它们叠在一起。不隔离变量，永远只能看见叠加后的噪声。**
